# codemap v2.1 — Shape, depth and clarity (spec change)

Date: 2026-10-18. Status: approved (user removed Branches and Watch out from Details). Changes `2026-10-17-codemap-v2-design.md`; where they conflict, this document wins.

## 1. Why

First real trace of a multi-stage job system (a large service with a request handler, a job queue and several pipeline stages) failed both anti-goals:

- 8 phases, most of them plumbing ("Key the request for idempotency", "Dispatch via outbox", "Run the job runner" whose steps repeat Walk/Split/Save).
- The core of the system — Resolve, Walk, Split inside the Build stage — never appeared. The walk stopped at the stage boundary after spending its hops on helpers.
- Cards showed long model text, clipped. No short description.
- Effects were free text ("S3 via ObjectStore.put", "Trace row") in a cramped lane, with confusing op letters (P, C).

Target shape, in codemap's own terms:

```text
1. Start trace   -> parse command, create trace row, start worker
2. Find entry
3. Walk & verify -> walk calls, record hops, verify indirect hops
4. Build levels   -> order path, split phases, split steps (and deeper)
5. Validate & save
```

## 2. Changes

### 2.1 Phases are the system's stages

- A phase is a major stage of the system: a workflow activity, a pipeline stage, a service boundary. Typical count 3–6. Hard cap 7.
- Plumbing is never its own phase: auth, request validation, idempotency keys, dedupe, outbox relay, workflow/job runners, run bookkeeping, status updates, retries. It becomes a step inside the phase it serves, or is left out when trivial.
- An orchestrator (workflow `run`, job runner, router) is not a node. Its order becomes the edges between phases.

### 2.2 Depth goes where the logic is

- Nodes nest to any depth: phase (level 0) → step (1) → sub-step (2) → … A node with its own recorded sub-path is expandable (▸).
- The walk runs in two passes:
  1. **Skeleton**: entry to end, stage level only; follow handoffs; do not descend into helpers. Small hop budget (default 40).
  2. **Deepen**: for each phase, walk inside it from its anchors. The budget per phase is weighted by how much logic it holds (lines of code in its anchored functions). Plumbing phases get little; core stages (e.g. Build levels) get most. Default total 160 hops.
- Splitting is recursive: a step whose sub-path has ≥ 3 points is split again into sub-steps, down to eager depth 3 (phase, step, sub-step). Deeper levels are built on click (same as lazy mode).
- Every hop, rule and verifier rule from v2 still applies at every level.

### 2.3 Nodes say what they do, briefly

- New field `summary`: one plain sentence, max 14 words, what the node does. Shown on the card.
- `title`: max 4 words, a verb phrase or the stage's own name ("Start trace", "Resolve entry"). Never a bare function name. The code name goes in Details.
- `does`, `input`, `output`, anchors, code: Details panel only.
- Code validates the length limits (submit retry on violation).

### 2.4 Effects: real names, read or write only

- `op` is `read` or `write` only. Write = insert, update, delete, put, publish, start a workflow, enqueue. Read = select, get, consume, fetch. An external API call is `read` unless it changes remote state.
- `target` is the real name: DB table (`db_table` / model name), bucket + key prefix (`uploads/<id>`), queue/topic, workflow name, cache key pattern, file path, external host or service name. Code normalises: strips words like "row", "via …", "table".
- UI: the bottom effect lane is removed. A **Data touched** drawer lists targets grouped by category; each row shows `R`/`W` per phase. Clicking a row highlights the nodes that touch it. Card chips: max 2 + `+N`, only `R`/`W`.

### 2.5 Cards never clip

- Card size comes from its content (title + summary + chips), measured before layout. ELK lays out measured sizes.
- Detail panel and Data drawer share one right-side panel with two tabs (Details, Data touched).

### 2.6 Details that explain the node

The Details tab is the place a developer learns the node. It holds:

| Section | Content |
| --- | --- |
| Header | title, summary, code name (`file:line symbol`) |
| How it works | 3–7 numbered steps in plain words. Each step cites the line(s) it describes (`extraction.py:1121`). |
| Input | type and key fields, and the node it comes from |
| Output | type and key fields, and the node it goes to |
| Data touched | each R/W with target, fields and line |
| Calls | callees; a callee that is a node in the graph is a link that moves the camera to it |
| Code | full function(s), line numbers; lines cited above and effect lines are highlighted |

- Generated by one model call per node, **on first open**, then stored. Input: the node's anchored code (full), its parent and sibling titles, its recorded hops and effects.
- Grounding: every cited line must lie inside the node's anchors or its recorded hops; code drops a bullet whose cite fails. No uncited claims.
- Panel shows a short loading state while the call runs. A failure shows the error with Retry; the deterministic parts (code, calls, data touched) always show.

## 3. Not changed

Recall-first hop rule, verifier, grounding, storage, server API shape (adds `summary` and deeper levels only), CLI.

## 4. Acceptance

- codemap self-trace: 3–6 phases matching Start trace / Find entry / Walk & verify / Build levels / Validate & save; Build levels contains Order path points, Split into phases, Split into steps (at level 1 or 2) anchored in `domain/rules.py`, `pipeline/split.py` and `pipeline/run.py`.
- No phase whose title is plumbing (idempotency, outbox, run workflow).
- Every node has a summary ≤ 14 words; every title ≤ 4 words.
- Effects show only R/W and real target names.
- Details for a step (e.g. Split into steps) has a How-it-works list with valid line cites and real input/output types.
- Visual check in the browser by the user.
